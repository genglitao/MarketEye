## "它" 能干什么

**你用日常语言描述想法，它就能帮你：**

- **生成需求文档**：你说"我想加个窗口自动吸附功能"，它帮你整理成结构化的 PRD 需求文档。
- **生成原型**：需求确认后，产出界面原型（本项目为桌面悬浮窗，原型以布局示意图 + 视觉状态说明为主）。
- **系统设计**：根据需求产出 SDD 设计文档，绘制层级、函数结构、配置字段都梳理明白。
- **写代码**：按设计文档编码，风格符合 `coding-rules.md`（纯标准库、`px()` 换算、Win32 类型声明）。
- **自动测试**：根据需求生成测试用例，接口用例跑脚本、界面用例截图取色验证。
- **生成操作手册**：功能上线后产出 SOP，用户照着就能操作。

**已有的系统也能管：**

- **老代码补文档**：读源码反推设计，再回溯需求，把历史欠账一次性补齐。
- **改功能**：你说要改什么，它找到相关文档，需求改完自动联动更新设计和测试文档。
- **修 Bug**：描述问题现象，直接定位修复。没文档的先帮你补上再修。

从新功能开发到老系统维护，覆盖软件全生命周期。

## 概述

`wiki` 是一个**软件交付面向人机协作的 SDLC（Software Development Life Cycle） 知识工程体系**。它将项目规范、业务流程、设计决策转化为 AI 可直接消费的结构化知识，从三个维度重塑开发协作：

- **人**：AI 按步骤产出，开发者逐步审查，确认后才继续。开发者全程掌控，消除"黑盒生成"的不确定性。
- **流程**：需求→设计→编码→测试环环相扣。每一步产出可追溯的版本文档以及代码，形成端到端知识与代码的闭环。
- **工具**：`rules/` 约束输出质量，`skills/` 控制执行流程，`docs/` 沉淀知识资产。为 Claude、Cursor、Trae 等 AI 工具提供统一的协作基准，切换工具不丢失上下文。

三大支柱承载上述能力：

- **规范 (rules)**：定义编码行为准则和文档编写标准，约束 AI 和开发者的输出质量。
- **技能 (skills)**：封装 SDLC 各环节（需求→设计→编码→测试）的流程逻辑，通过 `sdlc-skill` 统一路由。
- **文档 (docs)**：存放 PRD/PROTO/SDD/TC/SOP 及经验库，是业务知识的唯一可信源。

**核心流程**：任何开发任务先由 `sdlc-skill` 判断路由，再按需求→设计→编码→测试的顺序逐步推进，每一步完成后等待确认，不会自动跳到下一步。

> 完整文档索引见 [wiki.md](wiki.md) | 行为配置见 [Agentic.md](Agentic.md)

## 为什么需要 "它"

传统的人机协作是**问答式**的——人提问，AI 回答，人参考答案后自己动手。这种模式下有三个结构性缺陷：

- **知识随人走**：项目资料靠口口相传，人员流失意味着知识归零，交接成本极高。
- **上下文靠嘴说**：每次对话独立，AI 不记得项目规范和历史决策，人需要反复解释同样的背景。
- **产出成孤岛**：需求、设计、代码散落各处，无法形成可检索、可复用的结构化资产。

**将协作方式从"问答式"升级为"人指导 AI 干活"**。

在你与 AI 的协作中，AI 不再是回答问题的工具，而是在你审查和确认下，按需求→设计→编码→测试的完整流程，一步步产出结构化交付物的执行者。每一次分析需求、每一次功能开发，都不是从零开始——AI 读到的是项目沉淀已久的业务说明、技术规范和设计文档，它能把项目所有历史按需加载到上下文与你交流，给出符合项目风格、延续已有决策的输出。

**当 AI 拥有了记忆，协作就从"反复解释"变成了"持续积累"。**

这是一种复利效应——每一次产出的需求、设计和代码，都会沉淀为下一轮上下文。第 1 次协作时你需要向 AI 解释一切，到第 10 次时它已理解项目背景。积累越久，偏差越小、效率越高。

## 详细介绍

### 规范 (rules) — 约束输出质量

规范是项目的"法律文件"，定义 AI 和开发者必须遵守的行为准则。它不描述怎么做，只规定边界：

| 规范 | 核心约束 |
| --- | --- |
| **编码准则** | 代码风格、命名约定、架构模式——确保 AI 生成的代码符合项目标准 |
| **文档规范** | PRD/PROTO/SDD/TC/SOP 的章节结构、格式要求、版本编号规则——确保文档产出统一 |
| **UI 规范** | 色板、字体、间距、组件样式——确保原型和前端产出风格一致 |

规范由各 skill 按需自动加载，开发者无需每次对话重复说明。

### 技能 (skills) — 控制执行流程

技能是 SDLC 各环节的"操作手册"，封装了该环节的完整执行逻辑：输入检查 → 步骤引导 → 产出校验。

| 技能 | 职责 |
| --- | --- |
| **sdlc-skill** | 总调度，根据任务类型路由到对应环节技能，确保流程不跳步、不越级 |
| **prd-skill** | 需求分析，引导产出结构化的 PRD 文档，按需生成高保真 PROTO 原型 |
| **sdd-skill** | 技术设计，基于 PRD 产出可落地的 SDD 文档 |
| **coding-skill** | 编码实现，校验 PRD+SDD 版本对齐后执行编码 |
| **test-skill** | 测试验收，按 TC 逐项验证并生成测试报告 |

所有技能遵循同一原则：**每一步完成后必须等待确认，不会自动跳到下一步**。这确保了开发者对流程有完全控制权，同时 AI 产出的每一步都有据可查。

### 文档 (docs) — 沉淀知识资产

文档是项目业务知识的唯一可信源，也是解决"知识库难以建立"的核心机制：

```
每一次功能开发 → 自动产出 PRD + SDD + TC（测试通过后按需生成 SOP）
                ↓
          沉淀到 docs/ 对应目录
                ↓
     下一轮对话时 AI 自动读取历史文档作为上下文
                ↓
         知识复利：积累越久，协作效率越高
```

**正向流程**：需求 → 设计 → 编码 → 测试（通过后按需生成 SOP 操作手册），每步自动生成版本化文档。

**逆向补齐**：对于已有代码但缺失文档的模块，支持 SDD → PRD → TC 逆向推导，将散落的历史资产转化为结构化知识。

### 三者协作关系

```
rules (约束) ──→ skills (流程) ──→ docs (产出)
    ↑               │                │
    └───────────────┴────────────────┘
         持续沉淀，形成复利
```

规范约束每个 skill 的输出质量，skill 按规范引导生成文档，文档又成为下一轮对话的上下文——三者形成闭环，驱动知识库持续积累。

## 快速开始

### 接入 AI 工具

将 `wiki` 的规范和技能接入 AI 编码工具有两种方式：

| 方式 | 操作 | 具体路径 |
| --- | --- | --- |
| **方式一：复制配置文件** | 将 [Agentic.md](Agentic.md) 内容复制到工具的默认配置文件 | Claude Code → `CLAUDE.md`，Cursor → `.cursorrules`，Trae → `.trae` |
| **方式二：复制完整目录** | 将 `rules/`、`skills/` 复制到工具的项目配置路径 | Claude Code → `.claude/`，Cursor → `.cursor/`，Trae → `.trae/` |

> 方式一轻量快捷，适合只需基础规则约束的场景；方式二可实现完整 SDLC 流程控制。

### 新功能开发

**完整流程：需求 → 设计 → 编码 → 测试**

| 步骤 | 操作 | 说明 |
| --- | --- | --- |
| 1. 提出需求 | 描述要新增的功能，如"我要新增窗口自动吸附功能" | 自动由 `sdlc-skill` 路由到 `prd-skill`，整理需求并生成 PRD 文档。PRD 完成后会询问是否需要生成界面原型（PROTO） |
| 2. 开始设计 | 在上一步完成后，说"开始设计" | 路由到 `sdd-skill`，读取 PRD 后进行技术设计，生成 SDD 文档 |
| 3. 按设计实现 | 确认设计后，说"按设计实现" | 路由到 `coding-skill`，检查 PRD+SDD 版本对齐后编码实现 |
| 4. 开始测试 | 编码完成后，说"开始测试" | 路由到 `test-skill`，按 TC 逐项验收，生成测试报告 |

> ⚠️ **每一步完成后必须停下来等待你的明确指示**，不会自动跳到下一步。

### 变更已有功能

| 步骤 | 操作 | 说明 |
| --- | --- | --- |
| 1. 描述变更 | 说明要变更的功能，如"调整设备类型的字段" | `sdlc-skill` 会先读取现有 PRD，再路由到 `prd-skill` |
| 2. 根据版本状态处理 | 未发布版本：同版本内修改，级联更新下游文档<br>已发布版本：生成新版本文档 | 由 `prd-skill` 自动判断 PRD 头部的"版本状态"字段 |
| 3. 继续后续 | 依次说"开始设计"→"按设计实现"→"开始测试" | 已发布版本：版本号按变更类型递增；未发布版本：版本号不变 |

### Bug 修复

| 步骤 | 操作 | 说明 |
| --- | --- | --- |
| 1. 描述 Bug | 说明问题现象，如"设备类型列表加载失败" | `sdlc-skill` 根据 Bug 描述定位功能模块 |
| 2. 检查文档 | 自动查找该模块是否有 PRD | 有 PRD → 进入 `coding-skill` 修复，同步更新文档<br>无 PRD → 建议先补充需求文档 |
| 3. 修复验证 | 修复完成后说"开始测试" | 回归验证，确保修复未破坏现有功能 |

### 补齐文档（为已有代码补文档）

为已有代码补充文档时，按 **SDD → PRD → TC** 逆向推导：先反推设计，再回溯需求，最后补充测试。提示词需指明模块、源码路径和版本号，各 skill 会自动加载对应规范。

| 步骤 | 操作 | 提示词示例 |
| --- | --- | --- |
| 1. 梳理设计 | 分析现有源码，反推 SDD | "为【窗口缩放】功能生成 SDD 设计文档 v1.0.0，分析 `ticker.pyw` 中的 `_edge_hit` / `on_drag` / `_resize_live` 相关代码" |
| 2. 回溯需求 | 基于刚生成的 SDD，反推 PRD | "根据 `SDD-盯盘君-窗口缩放-v1.0.0.md` 反推生成 PRD 需求文档 v1.0.0" |
| 3. 补充测试 | 基于 PRD + SDD，生成 TC | "根据 `PRD-盯盘君-窗口缩放-v1.0.0` 和 `SDD-盯盘君-窗口缩放-v1.0.0` 生成测试 TC v1.0.0" |

> 本项目为单模块单文件程序，不涉及跨模块依赖；提示词中只需指明功能名与涉及的函数/方法即可。

### 纯技术任务

某些技术任务不涉及业务需求变更，可跳过 PRD：

| 场景 | 流程 |
| --- | --- |
| 纯技术框架设计 | 直接"设计 xxx" → sdd-skill |
| 纯技术变更实现 | 设计 → 编码（只需 SDD） |
| 临时技术任务 | 不创建额外文档，只同步更新过期文档 |
