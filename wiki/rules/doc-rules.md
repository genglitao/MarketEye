# 文档规范

> 本文件定义项目中文档的编写、同步和管理规范。**本文是 PRD/SDD/TC/SOP/PROTO 结构的唯一权威依据**，已有文档可能存在偏差，如有冲突以本文为准。

*最后更新: 2026-10-19*

***

## 1. 同步原则

**任何代码修改必须同步更新对应的文档**。代码与文档是共生关系，文档滞后者视为流程未完成。

**原型（PROTO）调整后，如与 PRD 业务逻辑不一致，必须同步更新 PRD**。原型与 PRD 保持一致，PRD 滞后视为流程未完成。

## 2. 文档类型与命名

| 层级 | 文件名格式 | 说明 |
| --- | --- | --- |
| 系统级 | `{类型}-系统{后缀}-v{版本号}.md` | 全局需求/设计 |
| 模块级 | `{类型}-{模块名}-v{版本号}.md` | 模块概要 |
| 功能级 | `{类型}-{模块名}-{功能名}-v{版本号}.md` | 具体功能详细文档 |

- `{类型}` 取值为 `PRD`、`SDD`、`TC`、`PROTO`、`SOP`
- `PROTO` 类型使用 `.html` 扩展名，其余类型使用 `.md`
- 模块名、功能名使用中文字符
- 版本号必须使用完整三段式 `v{x}.{y}.{z}`，禁止省略（如 `v1.0`）
- 经验库文档使用独立命名规则，详见 [5.4 经验库文档](#54-经验库文档)

## 4. 文档头部信息

每个文档必须包含：

```markdown
# {文档标题}

## 1. 文档概述

### 1.1 文档信息

| 字段 | 内容 |
| --- | --- |
| 项目名称 | xxx系统 |
| 文档版本 | v1.0.0 |
| 版本状态 | 未发布 |
| 创建日期 | YYYY-MM-DD |
| 更新日期 | YYYY-MM-DD |
| 基于需求 | PRD-xxx-v1.0.0 |

**版本状态取值**：

| 状态 | 含义 |
| --- | --- |
| 未发布 | 功能尚未发布至生产环境，允许同版本内反复调整 |
| 已发布 | 功能已发布至生产环境，版本冻结，修改必须升版本 |

### 1.2 变更记录

| 版本 | 日期 | 变更人 | 变更类型 | 关联章节 | 变更内容 |
| --- | --- | --- | --- | --- | --- |
| v1.1.0 | YYYY-MM-DD | - | 修改 | §3.2.3 | xxx功能补充 |
| v1.0.0 | YYYY-MM-DD | - | 新增 | — | 初始版本 |
```

**变更记录规则**：

- 每个文档版本对应且只能对应一行记录，版本号在同一文档的变更记录中必须唯一，按版本降序排列（最新在上）
- **未发布版本**：同版本内调整时，直接更新并合并该行记录，不新增行。变更内容应能完整反映本版本相对于上一版本的所有净变化
- **合并语义**：合并是**重写融合为净变化摘要**（按功能域概括最终形态、去重），不是在该行变更内容末尾增量追加。本版本开发过程中的中间态（本版本内加了又删的功能、被后续修改覆盖的表述）不入变更记录；关联章节按受影响章节融合为连续范围（如 `§3.2.1–§3.2.8`）
- **已发布版本**：版本冻结，行记录锁定，不可修改
- 变更人字段如无具体负责人填 `-`
- 文档交付和独立审核前必须检查变更记录版本号是否重复；存在重复版本号时审核不得通过

**字段说明**：

| 字段 | 说明 | 示例 |
| --- | --- | --- |
| 版本 | 文档版本号，三段式 | v1.1.0 |
| 日期 | 最近一次更新日期 | 2026-07-13 |
| 变更人 | 变更负责人，未知填 `-` | - |
| 变更类型 | `新增` / `修改` / `删除`，决定下游文档是新增还是修改对应部分 | 新增 |
| 关联章节 | 受影响的本体章节编号，多个用顿号分隔。帮助下游文档直接定位变更位置，无需全文比对 | §3.2.3、§3.3 状态机 |
| 变更内容 | 简述变更原因和涉及范围，不展开实现细节 | 审批驳回通知增加仅管理员可见的限制 |

> **例外**：经验库不在此列（见 5.4）。PROTO 为 HTML 文件，元数据应以 HTML 注释形式嵌入文件头部，字段参照本节的文档信息表。

## 5. 文档结构规范

除经验库外，PRD/SDD/TC/SOP 四类正式文档均遵循以下通用约定：

| 约定 | 说明 |
| --- | --- |
| 固定二级编号 | 采用**固定二级章节编号**，禁止自行调整顺序或增删章节 |
| 级别标注 | 各章标注 `[必须]` 或 `[按需]`；`[按需]` 根据模块实际情况决定是否包含 |
| 同级一致 | 同层级模块的同类型文档**必须保持二级章节编号一致** |
| mermaid 图表 | 文档中所有图表（架构图、流程图、时序图、ER 图、类图、状态图等）**必须使用 mermaid** 代码块绘制，禁止以截图或外部图片代替。mermaid 代码块使用 4 空格缩进，禁止 tab。**结构类图表（功能架构图、界面功能架构图、模块划分图等）使用左右布局 `graph LR`，禁止上下布局 `graph TD`**；流程/状态类图表（流程图、状态机图、时序图）按内容适配。mermaid 代码块属图表描述语言，**不视为 §7 所禁止的代码** |
| Markdown 表格 | **禁止**使用空格填充列宽做视觉对齐。分隔符 `|` 两侧各留一个空格，单元格内容前后不添加对齐空格 |

各类型详细结构如下：

### 5.1 PRD 需求文档

#### 第 1 章 — 文档概述 `[必须]`

| 编号 | 章节 | 内容 | 级别 |
| --- | --- | --- | :--: |
| 1.1 | 文档信息 | 文档版本、创建/更新日期、基于需求 | 必须 |
| 1.2 | 变更记录 | 版本降序，每版一行 | 必须 |
| 1.3 | 项目背景 | 业务背景、要解决的核心问题 | 必须 |
| 1.4 | 功能概述 | 功能范围、核心能力描述 | 必须 |
| 1.5 | 目标用户 | 用户角色定义、各角色使用场景 | 必须 |

#### 第 2 章 — 需求全景 `[必须]`

| 编号 | 章节 | 内容 | 级别 |
| --- | --- | --- | :--: |
| 2.1 | 功能架构 | 使用 mermaid 功能结构图展示功能的层次关系和整体组成，让读者在进入细节前建立全局认知 | 必须 |
| 2.2 | 功能模块划分 | 各功能域的职责范围与边界，说明每个功能域解决什么问题、包含哪些子功能 | 必须 |
| 2.3 | 功能依赖关系 | 功能域之间的前置依赖和关联关系（如 A 功能的数据需 B 功能先配置），使用 mermaid 绘制依赖图 | 必须 |
| 2.4 | 界面功能架构 | 定义悬浮窗的界面区块与入口（标题栏 / 列表区 / 滚动条 / 右键菜单项 / 自选管理面板）与「入口—功能点」映射，作为 PROTO 与 SDD 界面设计的依据 | 必须 |

> **2.4 界面功能架构**：本项目无网页导航菜单，入口只有三类——**窗口区块**（标题栏、列表区、滚动条）、**右键菜单项**、**自选管理面板中的控件**。PRD 必须显式列出全部入口，作为 PROTO 与 SDD §3.5 界面设计的依据。要求：
>
> - 用 mermaid 绘制入口结构，入口名称与最终产品文案一致（右键菜单项的 label 即产品文案）；该结构描述「用户从哪里触发功能」，**区别于 §2.1 功能架构图**（业务能力层次）
> - **入口层级定义**：一级 = 窗口区块；二级 = 区块内的可交互元素（如列表行、滚动条滑块）或右键菜单项；三级 = 面板内的具体控件（如「管理自选」面板中的搜索框、添加按钮）
> - 用映射表逐项列出：入口名称、所在层级、触发方式（点击 / 双击 / 拖动 / 滚轮 / 右键）、功能路径（§3.2）、对应功能点（§3.2 F-xx）、对应功能域（§2.2 M-xx）
> - **与 §3.2 功能路径的关系**：§3.2 功能路径是功能的逻辑层级，§2.4 是用户触发入口，两者须通过映射表的「功能路径」列一一对应，不得出现两套互不关联的层级
> - 映射完整性：每个入口必须对应至少一个功能点；一个功能点可有多个入口（多入口须显式标注）；不得出现无功能点的入口或无入口的功能点
> - **一致性校验方法**：PROTO 的界面元素、SDD §3.5 的元素清单必须逐项对照本表核验（名称、层级、触发方式、对应功能点四项一致），不得自行增删改
> - 如需调整入口，先改 PRD 本表并级联更新 PROTO/SDD

#### 第 3 章 — 功能需求 `[必须]`

| 编号 | 章节 | 内容 | 级别 |
| --- | --- | --- | :--: |
| 3.1 | 用户故事 | 角色-活动-价值格式的用户故事 | 必须 |
| 3.2 | 详细功能点 | 每个功能点独立成节，包含：功能路径（`一级 → 二级 → 三级`）、功能描述、触发条件、输入字段定义表（字段名/类型/必填/校验规则/默认值/说明）、业务处理逻辑（步骤/条件分支/状态变更）、输出结果（成功/失败反馈/副作用）、交互流程。禁止将多个功能压缩为一行表格记录 | 必须 |
| 3.3 | 业务规则 | 按子功能域分节，每节包含：业务约束（约束条件/适用范围/违反处理）、业务状态机（状态列表含编码含义 + mermaid stateDiagram 流转图 + 每个流转的前置条件与触发动作）、业务逻辑规则（触发条件/执行动作/优先级）。禁止仅罗列零散列表项 | 必须 |
| 3.4 | 业务流程 | 端到端业务操作链路，使用 mermaid 流程图或用户旅程图，展示功能之间的串联关系和用户操作路径（如"制定计划 → 提交审批 → 触发任务 → 执行巡检 → 审核结果"）。区别于 SDD 的技术实现级流程，PRD 流程聚焦用户视角的业务闭环 | 必须 |

> **3.2 字段定义表**：涉及数据录入/展示的功能点，输入和输出字段必须以表格形式逐字段定义，禁止仅用自然语言概述。字段表至少包含：字段名、类型（文本/数字/下拉单选/下拉多选/日期/布尔等）、必填（是/否）、校验规则（格式/长度/取值范围/唯一性）、默认值、字段说明。
>
> **3.2 功能路径**：功能路径格式为 `一级 → 二级 → 三级`（层级数按实际情况，不强制三级）。功能路径描述功能点在系统中的层级位置（纯功能层级，非 UI 菜单名、非 URL 路由）。任意层级都可能是功能页面。不确定时向用户确认。
>
> **3.3 编写要求**：
>
> - **业务约束**：须包含约束条件、适用范围、违反时的处理方式（阻止操作 / 警告但允许 / 允许并记录日志）
> - **业务状态机**：须包含状态列表（状态名/编码/含义）、mermaid stateDiagram 流转图、每个流转的前置条件和触发动作（谁可触发 / 操作入口 / 触发后系统做什么）
> - **业务逻辑规则**：须包含触发条件、执行动作、优先级（多条规则冲突时的裁决顺序）
>
> **3.2 与 3.3 的边界**：3.2 描述单个功能的字段级定义和操作步骤；3.3 描述跨功能的业务规则（如状态如何流转、删除关联数据时级联策略、配置变更如何传播）。
>
> PRD 内容边界：只描述"做什么"，不涉及"怎么做"。禁止包含第三方接口地址、`config.json` 字段结构、函数/类名、Python 版本与库名。

#### 第 4 章 — 非功能性需求 `[必须]`

| 编号 | 章节 | 内容 | 级别 |

| 4.3 | 兼容性要求 | Windows 版本、DPI 缩放比例（100%~200%）、屏幕分辨率下限、多显示器 | 按需 |

### 5.2 SDD 设计文档

#### 第 1 章 — 文档概述 `[必须]`

| 编号 | 章节 | 内容 | 级别 |
| --- | --- | --- | :--: |
| 1.1 | 文档信息 | 文档版本、创建/更新日期、基于需求、基于设计 | 必须 |
| 1.2 | 变更记录 | 版本降序，每版一行 | 必须 |
| 1.3 | 技术选型 | Python 版本、GUI 框架（tkinter）、数据来源（腾讯行情接口）、配置存储（JSON 文件） | 必须 |
| 1.4 | 文档目的 | 本模块设计目标、要解决的问题、模块职责范围 | 必须 |

#### 第 2 章 — 系统架构 `[必须]`

| 编号 | 章节 | 内容 | 级别 |
| --- | --- | --- | :--: |
| 2.1 | 整体架构 | 系统分层架构图 | 必须 |
| 2.2 | 模块划分 | 模块拆分方案、各模块职责与边界 | 必须 |
| 2.3 | 分层职责 | 窗口与绘制层（tkinter Canvas）/ 行情获取层（urllib + 腾讯接口）/ 配置与持久化层（config.json、position.json）/ 交互层（鼠标事件与右键菜单）等各层职责说明 | 必须 |
| 2.4 | 界面区块地图 | 悬浮窗的区块划分（标题栏 / 列表区 / 滚动条 / 右键菜单 / 自选管理面板）、区块与绘图层级的对应关系；各区块须回链 PRD §2.4 的界面功能架构 | 必须 |

#### 第 3 章 — 详细设计 `[必须]`

| 编号 | 章节 | 内容 | 级别 |
| --- | --- | --- | :--: |

### 6.2 PRD — 回答"做什么"

**应包含**：功能概述和业务目标、用户故事和角色、业务规则、业务流程（用户视角端到端链路）、验收标准、非功能性需求描述

**不应包含**：接口地址/参数/返回报文、`config.json` 字段结构、类名/方法名、技术选型和库名、技术实现级流程图（函数调用/数据流转）

> 章节结构以 [§5.1 PRD 结构模板](#51-prd-需求文档) 为准。

### 6.3 SDD — 回答"怎么做"

**应包含**：技术选型和库、系统架构与分层、外部接口设计、配置文件结构、类与函数设计、流程图/时序图/架构图/类图（详见 §5.2）、依赖关系、运行与发布配置、错误处理

**不应包含**：用户故事和角色定义、非技术性的业务规则解释

> 章节结构以 [§5.2 SDD 结构模板](#52-sdd-设计文档) 为准。

### 6.4 TC — 回答"如何验证"

**应包含**：对照 PRD 验收标准的测试用例、功能测试用例（含边界条件和异常场景）、接口测试用例（含测试数据和预期结果）、非功能测试用例（性能/安全/兼容性）、回归测试验证点、测试执行记录和缺陷跟踪

**不应包含**：业务功能描述和用户故事（属 PRD）、技术实现细节（属 SDD）、非测试类的源代码

> 章节结构以 [§5.3 TC 结构模板](#53-tc-测试文档) 为准。

### 6.5 PROTO — 回答"长什么样"

**应包含**：基于 ui-rules.md 的窗口布局和视觉风格、PRD 描述的所有交互状态（默认/悬停/按下/拖拽中/禁用/加载中/空数据/连接失败）、可交互区域的热区示意

**入口约束**：PROTO 的界面区块与右键菜单项必须与 PRD §2.4 界面功能架构完全一致（名称、层级、触发方式、对应功能点），不得自行增删改；如原型中发现入口需要调整，须先回改 PRD §2.4 再同步 PROTO

**不应包含**：行情解析与计算逻辑、Win32 调用实现代码、SDD 级别的技术实现细节

### 6.6 SOP — 回答"怎么用"

**应包含**：运行环境要求（操作系统/Python/网络）、场景化操作步骤及截图、常见问题及解答、术语表

**不应包含**：接口地址/配置结构（属 SDD）、用户故事（属 PRD）、测试断言（属 TC）

> 章节结构以 [§5.5 SOP 结构模板](#55-sop-操作手册) 为准。

## 8. 版本管理

### 8.1 版本号格式

| 规则 | 说明 |
| --- | --- |
| 格式 | 必须使用完整三段式 `v{x}.{y}.{z}` |
| 主版本 | 架构变化或重大功能重组时递增 |
| 次版本 | 功能调整（业务逻辑字段增删）时递增 |
| 补丁版本 | 小改动时递增 |
| 禁止 | 不得省略任何一段，如 `v1.0`、`v1.1` 都是错误写法 |

### 8.2 版本迭代规则

| 变更类型 | 版本规则 | 说明 |
| --- | --- | --- |
| 纯样式调整 | 无需版本迭代 | 代码格式化、注释修正、日志文案调整 |
| 小改动（UI交互变更、字段增删） | 补丁版本 v1.0.x | 不影响核心逻辑的调整 |
| 功能调整（业务逻辑变更） | 次版本 v1.x.0 | 影响业务功能的变更 |
| 大重构（架构变化、功能重组） | 主版本 v2.0.0 | 架构调整、模块重组 |

### 8.3 版本状态与冻结

**版本冻结的唯一触发条件：功能已发布至生产环境。**

| 规则 | 说明 |
| --- | --- |
| 未发布 | 允许同版本内反复调整，调整时更新该行变更记录（不新增行），必须级联更新所有下游文档（SDD/TC/PROTO/SOP/代码） |
| 已发布 | 版本冻结，禁止原地修改；任何变更必须升版本，保留旧版以支持追溯与回滚 |
| 状态变更触发 | 由用户手动触发：用户确认功能已发布至生产环境后告知AI，AI批量更新该版本所有文档的状态字段及变更记录 |
| 状态变更提醒 | test-skill 测试通过后自动提醒用户发布后更新版本状态 |

**状态变更示例**：

```markdown
| 版本 | 日期 | 变更人 | 变更类型 | 关联章节 | 变更内容 |
| --- | --- | --- | --- | --- | --- |
| v1.0.0 | 2026-05-20 | - | 新增 | — | 完成初始建设及审批规则调整，已发布 |
```

> 未发布期间调整 v1.0.0 时，直接修改该行日期和变更内容。发布时将版本状态改为"已发布"，变更内容追加"已发布"标记。

### 8.4 版本统一要求

**迭代时新增文档，保留旧版。PRD/SDD/TC/PROTO/SOP 必须使用统一版本号。**

| 要求 | 说明 |
| --- | --- |
| 新增文档 | 版本迭代时，创建新版本文档，保留旧版 |
| 版本统一 | PRD、SDD、TC、PROTO、SOP 必须使用相同版本号 |
| 版本对照 | PRD v1.0.0 → PROTO v1.0.0 → SDD v1.0.0 → TC v1.0.0 → SOP v1.0.0 |

| 场景 | 操作 | 说明 |
| --- | --- | --- |

### 10.1 适用判断（跨模块场景）

一个 PRD 涉及**两个及以上模块**有新设计工作时，触发本规范。若只有一个模块有新设计、其他模块纯复用现有接口，不适用本规范——直接在单模块 SDD 中说明外部调用即可。

### 10.2 规则

#### ① PRD 放在主导模块下

PRD 放在主导模块下。判断标准：谁驱动端到端流程的推进，谁就是主导方。不确定时，选用户入口所在的模块。

```
└── PRD-{主导模块}-{业务场景}-v{x}.{y}.{z}.md
```

PRD 内容覆盖端到端业务流程，包含所有参与模块的职责描述和模块间交互的业务规则。

#### ② 每个参与模块各写一份 SDD，与 PRD 同版本

```
docs/设计文档/{模块名}/{业务场景}/v{x}.{y}.{z}/
└── SDD-{模块名}-{业务场景}-v{x}.{y}.{z}.md
```

PRD 与各模块 SDD 使用统一版本号，遵循 [§8.4 版本统一要求](#84-版本统一要求)。各模块 SDD 的"文档依赖"（第 8 章）中锁定被依赖 SDD 的**具体版本号**，不写范围（如 `>= v1.2.0`）。

#### ③ "模块间交互"与"文档依赖"升级为必须

参与跨模块业务的 SDD，其第 7 章（模块间交互）和第 8 章（文档依赖）由 `[按需]` 升级为 `[必须]`。

- **模块间交互**：从本模块视角描述交互关系表（交互方向/对方模块/接口或消息/调用时机/数据流向）和 mermaid 时序图。同一交互在各模块 SDD 中冗余出现——这是有意冗余，目的是每份文档自包含。

#### ④ 被依赖的 SDD 升级时写版本影响分析

不区分文档类别。一份 SDD 只要被其他文档的"文档依赖"章节引用过，其第 9 章（版本影响分析）即升级为 `[必须]`——此后每次升级都必须在文末追加影响记录：

- 本项目为**单文件程序**（`ticker.pyw`），所有逻辑在同一文件内按类与方法组织；新增功能优先以**新方法**扩展对应类，不拆文件
- 若将来代码量增长需要拆分模块，按「行情获取 / 界面绘制 / 配置与持久化 / 交互」四层拆包，跨模块通过函数调用（非消息）协作
- 共享常量与主题配置集中在文件头部（`THEMES`、`KEY`、尺寸常量），不散落在各方法内

### 10.5 规则总览

| # | 规则 |
| - | ---------------------------- |
| ① | PRD 放在主导模块下 |
| ② | 每个参与模块各写一份 SDD，与 PRD 同版本 |
| ③ | "模块间交互"和"文档依赖"在跨模块时升级为必须 |
| ④ | 被其他文档依赖的 SDD，升级时必须写版本影响分析 |
| ⑤ | wiki.md 中跨模块场景独立建 H3，标注"跨模块" |

## 11. 业务开发 vs 临时任务

| 场景 | 文档要求 | 说明 |
| --- | --- | --- |
| **业务功能开发** | 必须创建文档 | 走 SDLC 流程：PRD/SDD/TC 缺一不可 |
| **补齐文档** | 按需创建文档 | 为已有代码补齐缺失的 PRD/SDD/TC |
| **临时技术任务** | 同步更新即可 | 不创建额外文档，如导致现有文档过期则同步更新 |
| **Bug修复** | 按影响决定 | 有对应功能的 PRD 则同步更新，否则无需创建新文档 |
