# 文档规范

> 本文件定义项目中文档的编写、同步和管理规范。**本文是 PRD/SDD/TC/SOP/PROTO 结构的唯一权威依据**，已有文档可能存在偏差，如有冲突以本文为准。

*最后更新: 2026-10-19*

***

## 1. 同步原则

**任何代码修改必须同步更新对应的文档**。代码与文档是共生关系，文档滞后者视为流程未完成。

**原型（PROTO）调整后，如与 PRD 业务逻辑不一致，必须同步更新 PRD**。原型与 PRD 保持一致，PRD 滞后视为流程未完成。

## 2. 文档类型与命名

| 层级 | 文件名格式 | 说明 |
| --- | --- | --- |
| 系统级 | `{类型}-系统{后缀}-v{版本号}.md` | 全局需求/设计 |
| 模块级 | `{类型}-{模块名}-v{版本号}.md` | 模块概要 |
| 功能级 | `{类型}-{模块名}-{功能名}-v{版本号}.md` | 具体功能详细文档 |

- `{类型}` 取值为 `PRD`、`SDD`、`TC`、`PROTO`、`SOP`
- `PROTO` 类型使用 `.html` 扩展名，其余类型使用 `.md`
- 模块名、功能名使用中文字符
- 版本号必须使用完整三段式 `v{x}.{y}.{z}`，禁止省略（如 `v1.0`）
- 经验库文档使用独立命名规则，详见 [5.4 经验库文档](#54-经验库文档)

## 4. 文档头部信息

每个文档必须包含：

```markdown
# {文档标题}

## 1. 文档概述

### 1.1 文档信息

| 字段 | 内容 |
| --- | --- |
| 项目名称 | xxx系统 |
| 文档版本 | v1.0.0 |
| 版本状态 | 未发布 |
| 创建日期 | YYYY-MM-DD |
| 更新日期 | YYYY-MM-DD |
| 基于需求 | PRD-xxx-v1.0.0 |

**版本状态取值**：

| 状态 | 含义 |
| --- | --- |
| 未发布 | 功能尚未发布至生产环境，允许同版本内反复调整 |
| 已发布 | 功能已发布至生产环境，版本冻结，修改必须升版本 |

### 1.2 变更记录

| 版本 | 日期 | 变更人 | 变更类型 | 关联章节 | 变更内容 |
| --- | --- | --- | --- | --- | --- |
| v1.1.0 | YYYY-MM-DD | - | 修改 | §3.2.3 | xxx功能补充 |
| v1.0.0 | YYYY-MM-DD | - | 新增 | — | 初始版本 |
```

**变更记录规则**：

- 每个文档版本对应且只能对应一行记录，版本号在同一文档的变更记录中必须唯一，按版本降序排列（最新在上）
- **未发布版本**：同版本内调整时，直接更新并合并该行记录，不新增行。变更内容应能完整反映本版本相对于上一版本的所有净变化
- **合并语义**：合并是**重写融合为净变化摘要**（按功能域概括最终形态、去重），不是在该行变更内容末尾增量追加。本版本开发过程中的中间态（本版本内加了又删的功能、被后续修改覆盖的表述）不入变更记录；关联章节按受影响章节融合为连续范围（如 `§3.2.1–§3.2.8`）
- **已发布版本**：版本冻结，行记录锁定，不可修改
- 变更人字段如无具体负责人填 `-`
- 文档交付和独立审核前必须检查变更记录版本号是否重复；存在重复版本号时审核不得通过

**字段说明**：

| 字段 | 说明 | 示例 |
| --- | --- | --- |
| 版本 | 文档版本号，三段式 | v1.1.0 |
| 日期 | 最近一次更新日期 | 2026-07-13 |
| 变更人 | 变更负责人，未知填 `-` | - |
| 变更类型 | `新增` / `修改` / `删除`，决定下游文档是新增还是修改对应部分 | 新增 |
| 关联章节 | 受影响的本体章节编号，多个用顿号分隔。帮助下游文档直接定位变更位置，无需全文比对 | §3.2.3、§3.3 状态机 |
| 变更内容 | 简述变更原因和涉及范围，不展开实现细节 | 审批驳回通知增加仅管理员可见的限制 |

> **例外**：经验库不在此列（见 5.4）。PROTO 为 HTML 文件，元数据应以 HTML 注释形式嵌入文件头部，字段参照本节的文档信息表。

> **按需加载**：原 §5「文档结构规范」（PRD/SDD/TC/PROTO 章节骨架，27.7 KB）已拆分至
> [doc-templates.md](doc-templates.md)。**创建或大幅修订文档时**才读取该文件；
> 本文件保留全部规则性内容（§1-§4、§6-§11）。

## 6. 文档内容边界规则

### 6.1 PRD vs SDD 内容边界

| 内容类型 | PRD (需求文档) | SDD (设计文档) |
| --- | --- | --- |
| **接口定义（地址/参数/返回报文）** | ❌ 禁止 | ✅ 必须 |
| **请求/响应示例** | ❌ 禁止 | ✅ 必须 |
| **业务功能描述** | ✅ 必须 | ❌ 禁止 |
| **用户故事** | ✅ 必须 | ❌ 禁止 |
| **验收标准** | ✅ 必须 | ❌ 禁止 |
| **配置文件结构（`config.json` 字段）** | ❌ 禁止 | ✅ 必须 |
| **类与函数结构** | ❌ 禁止 | ✅ 必须 |
| **技术流程图**（系统内部调用/数据流转） | ❌ 禁止 | ✅ 必须 |
| **业务流程图**（用户视角业务闭环） | ✅ 必须 | ✅ 必须 |
| **技术选型** | ❌ 禁止 | ✅ 必须 |
| **性能指标** | ✅ 必须 | ✅ 必须 |
| **错误码定义** | ❌ 禁止 | ✅ 必须 |

### 6.2 PRD — 回答"做什么"

**应包含**：功能概述和业务目标、用户故事和角色、业务规则、业务流程（用户视角端到端链路）、验收标准、非功能性需求描述

**不应包含**：接口地址/参数/返回报文、`config.json` 字段结构、类名/方法名、技术选型和库名、技术实现级流程图（函数调用/数据流转）

> 章节结构以 [§5.1 PRD 结构模板](#51-prd-需求文档) 为准。

### 6.3 SDD — 回答"怎么做"

**应包含**：技术选型和库、系统架构与分层、外部接口设计、配置文件结构、类与函数设计、流程图/时序图/架构图/类图（详见 §5.2）、依赖关系、运行与发布配置、错误处理

**不应包含**：用户故事和角色定义、非技术性的业务规则解释

> 章节结构以 [§5.2 SDD 结构模板](#52-sdd-设计文档) 为准。

### 6.4 TC — 回答"如何验证"

**应包含**：对照 PRD 验收标准的测试用例、功能测试用例（含边界条件和异常场景）、接口测试用例（含测试数据和预期结果）、非功能测试用例（性能/安全/兼容性）、回归测试验证点、测试执行记录和缺陷跟踪

**不应包含**：业务功能描述和用户故事（属 PRD）、技术实现细节（属 SDD）、非测试类的源代码

> 章节结构以 [§5.3 TC 结构模板](#53-tc-测试文档) 为准。

### 6.5 PROTO — 回答"长什么样"

**应包含**：基于 ui-rules.md 的窗口布局和视觉风格、PRD 描述的所有交互状态（默认/悬停/按下/拖拽中/禁用/加载中/空数据/连接失败）、可交互区域的热区示意

**入口约束**：PROTO 的界面区块与右键菜单项必须与 PRD §2.4 界面功能架构完全一致（名称、层级、触发方式、对应功能点），不得自行增删改；如原型中发现入口需要调整，须先回改 PRD §2.4 再同步 PROTO

**不应包含**：行情解析与计算逻辑、Win32 调用实现代码、SDD 级别的技术实现细节

### 6.6 SOP — 回答"怎么用"

**应包含**：运行环境要求（操作系统/Python/网络）、场景化操作步骤及截图、常见问题及解答、术语表

**不应包含**：接口地址/配置结构（属 SDD）、用户故事（属 PRD）、测试断言（属 TC）

> 章节结构以 [§5.5 SOP 结构模板](#55-sop-操作手册) 为准。

## 7. SDD 代码引用规则

**SDD 设计文档中禁止直接包含代码**，应通过源码引用指向源代码文件。

| 做法 | 要求 |
| --- | --- |
| ❌ 禁止 | 在 SDD 中直接粘贴代码（Python 源码、JSON 配置等） |
| ✅ 必须 | 以纯文本标注源码位置，路径以项目根为起点，如 `ticker.pyw / Panel.paint()`、`config.json / groups[].items` |

| 文档类型 | 代码要求 |
| --- | --- |
| PRD | ❌ 禁止包含任何代码 |
| SDD | ✅ 引用源码，禁止粘贴代码 |
| TC | ✅ 可包含测试代码片段 |
| PROTO | ✅ 必须包含完整代码（HTML/CSS/JS），单文件自包含 |

> **mermaid 豁免**：mermaid 代码块属图表描述语言（DSL），不视为本规则所定义的"代码"。该豁免与 API 响应示例（` ```json `）同级适用。

## 8. 版本管理

### 8.1 版本号格式

| 规则 | 说明 |
| --- | --- |
| 格式 | 必须使用完整三段式 `v{x}.{y}.{z}` |
| 主版本 | 架构变化或重大功能重组时递增 |
| 次版本 | 功能调整（业务逻辑字段增删）时递增 |
| 补丁版本 | 小改动时递增 |
| 禁止 | 不得省略任何一段，如 `v1.0`、`v1.1` 都是错误写法 |

### 8.2 版本迭代规则

| 变更类型 | 版本规则 | 说明 |
| --- | --- | --- |
| 纯样式调整 | 无需版本迭代 | 代码格式化、注释修正、日志文案调整 |
| 小改动（UI交互变更、字段增删） | 补丁版本 v1.0.x | 不影响核心逻辑的调整 |
| 功能调整（业务逻辑变更） | 次版本 v1.x.0 | 影响业务功能的变更 |
| 大重构（架构变化、功能重组） | 主版本 v2.0.0 | 架构调整、模块重组 |

### 8.3 版本状态与冻结

**版本冻结的唯一触发条件：功能已发布至生产环境。**

| 规则 | 说明 |
| --- | --- |
| 未发布 | 允许同版本内反复调整，调整时更新该行变更记录（不新增行），必须级联更新所有下游文档（SDD/TC/PROTO/SOP/代码） |
| 已发布 | 版本冻结，禁止原地修改；任何变更必须升版本，保留旧版以支持追溯与回滚 |
| 状态变更触发 | 由用户手动触发：用户确认功能已发布至生产环境后告知AI，AI批量更新该版本所有文档的状态字段及变更记录 |
| 状态变更提醒 | test-skill 测试通过后自动提醒用户发布后更新版本状态 |

**状态变更示例**：

```markdown
| 版本 | 日期 | 变更人 | 变更类型 | 关联章节 | 变更内容 |
| --- | --- | --- | --- | --- | --- |
| v1.0.0 | 2026-05-20 | - | 新增 | — | 完成初始建设及审批规则调整，已发布 |
```

> 未发布期间调整 v1.0.0 时，直接修改该行日期和变更内容。发布时将版本状态改为"已发布"，变更内容追加"已发布"标记。

### 8.4 版本统一要求

**迭代时新增文档，保留旧版。PRD/SDD/TC/PROTO/SOP 必须使用统一版本号。**

| 要求 | 说明 |
| --- | --- |
| 新增文档 | 版本迭代时，创建新版本文档，保留旧版 |
| 版本统一 | PRD、SDD、TC、PROTO、SOP 必须使用相同版本号 |
| 版本对照 | PRD v1.0.0 → PROTO v1.0.0 → SDD v1.0.0 → TC v1.0.0 → SOP v1.0.0 |

## 9. 文档更新规则

| 场景 | 操作 | 说明 |
| --- | --- | --- |
| 版本升级（已发布版本变更） | 创建新版本文档，保留旧版 | PRD/PROTO/SDD/TC/SOP |
| 同版本调整（未发布版本变更） | 在当前版本内更新，级联更新下游文档 | PRD/PROTO/SDD/TC/SOP；更新并合并当前版本已有变更记录，禁止追加重复版本行 |
| 测试记录更新 | 在当前版本内追加，不创建新版本 | TC 中测试执行结果以追加方式更新，不影响版本号；同一版本允许多轮测试记录并存 |
| 经验库更新 | 直接修改，无需版本号 | 经验库文档不纳入版本管理，新增或修改经验直接编辑即可 |
| wiki.md 同步 | **必须在文档产出/变更后同步更新 wiki.md**。wiki.md 采用分组列表格式，每条为 `- [文档名](相对路径) — 一句话摘要`。功能级文档按模块+功能定位到对应 H3/H4 标题下追加条目（无则新增标题）；系统级/模块级文档更新到"全局"区域；经验库文档更新到"经验库"区域 | PRD/PROTO/SDD/TC/SOP/经验库的所有新增或变更 |

## 10. 文档组织规范

> **本项目为单模块工程**（单文件桌面程序 `ticker.pyw` + 两个 JSON 配置），模块名统一为 `盯盘君`。
> 功能级文档**不使用"模块层"中间目录**，直接按 `docs/{类型}文档/{功能名}/v{x}.{y}.{z}/` 组织：

```
docs/
├── 需求文档/自选管理/v1.0.0/
│   ├── PRD-盯盘君-自选管理-v1.0.0.md
│   └── PROTO-盯盘君-自选管理-v1.0.0.html
├── 设计文档/自选管理/v1.0.0/
│   └── SDD-盯盘君-自选管理-v1.0.0.md
└── 测试文档/自选管理/v1.0.0/
    ├── TC-盯盘君-自选管理-v1.0.0.md
    ├── screenshots/
    └── scripts/            # 界面验证脚本（如 PIL 截图取色、坐标采样）
```

> 文档文件名仍保留 `{模块名}` 段（统一写 `盯盘君`），便于将来拆分模块时迁移。
>
> 下方 §10.1–§10.5 为**跨模块场景**规则，**当前项目不触发**，保留以备将来拆分多模块时启用。

### 10.1 适用判断（跨模块场景）

一个 PRD 涉及**两个及以上模块**有新设计工作时，触发本规范。若只有一个模块有新设计、其他模块纯复用现有接口，不适用本规范——直接在单模块 SDD 中说明外部调用即可。

### 10.2 规则

#### ① PRD 放在主导模块下

PRD 放在主导模块下。判断标准：谁驱动端到端流程的推进，谁就是主导方。不确定时，选用户入口所在的模块。

```
docs/需求文档/{主导模块}/{业务场景}/v{x}.{y}.{z}/
└── PRD-{主导模块}-{业务场景}-v{x}.{y}.{z}.md
```

PRD 内容覆盖端到端业务流程，包含所有参与模块的职责描述和模块间交互的业务规则。

#### ② 每个参与模块各写一份 SDD，与 PRD 同版本

```
docs/设计文档/{模块名}/{业务场景}/v{x}.{y}.{z}/
└── SDD-{模块名}-{业务场景}-v{x}.{y}.{z}.md
```

PRD 与各模块 SDD 使用统一版本号，遵循 [§8.4 版本统一要求](#84-版本统一要求)。各模块 SDD 的"文档依赖"（第 8 章）中锁定被依赖 SDD 的**具体版本号**，不写范围（如 `>= v1.2.0`）。

#### ③ "模块间交互"与"文档依赖"升级为必须

参与跨模块业务的 SDD，其第 7 章（模块间交互）和第 8 章（文档依赖）由 `[按需]` 升级为 `[必须]`。

- **模块间交互**：从本模块视角描述交互关系表（交互方向/对方模块/接口或消息/调用时机/数据流向）和 mermaid 时序图。同一交互在各模块 SDD 中冗余出现——这是有意冗余，目的是每份文档自包含。
- **文档依赖**：声明本设计依赖的其他 SDD 及具体版本号，格式为四列表格（依赖文档/版本/依赖内容/用途）。

#### ④ 被依赖的 SDD 升级时写版本影响分析

不区分文档类别。一份 SDD 只要被其他文档的"文档依赖"章节引用过，其第 9 章（版本影响分析）即升级为 `[必须]`——此后每次升级都必须在文末追加影响记录：

```markdown
### v1.2.0 → v1.3.0

| 字段 | 内容 |
|------|------|
| 变更类型 | 接口参数变更 / 新增字段 / 行为变更 / 废弃 |
| 变更描述 | 具体变更内容 |
| 影响范围 | 受影响的其他文档列表 |
| 改造方案 | 各受影响方的改造指引 |
```

### 10.4 代码侧对应

文档组织方式不影响代码组织：

- 本项目为**单文件程序**（`ticker.pyw`），所有逻辑在同一文件内按类与方法组织；新增功能优先以**新方法**扩展对应类，不拆文件
- 若将来代码量增长需要拆分模块，按「行情获取 / 界面绘制 / 配置与持久化 / 交互」四层拆包，跨模块通过函数调用（非消息）协作
- 共享常量与主题配置集中在文件头部（`THEMES`、`KEY`、尺寸常量），不散落在各方法内

### 10.5 规则总览

| # | 规则 |
| - | ---------------------------- |
| ① | PRD 放在主导模块下 |
| ② | 每个参与模块各写一份 SDD，与 PRD 同版本 |
| ③ | "模块间交互"和"文档依赖"在跨模块时升级为必须 |
| ④ | 被其他文档依赖的 SDD，升级时必须写版本影响分析 |
| ⑤ | wiki.md 中跨模块场景独立建 H3，标注"跨模块" |

## 11. 业务开发 vs 临时任务

| 场景 | 文档要求 | 说明 |
| --- | --- | --- |
| **业务功能开发** | 必须创建文档 | 走 SDLC 流程：PRD/SDD/TC 缺一不可 |
| **补齐文档** | 按需创建文档 | 为已有代码补齐缺失的 PRD/SDD/TC |
| **临时技术任务** | 同步更新即可 | 不创建额外文档，如导致现有文档过期则同步更新 |
| **Bug修复** | 按影响决定 | 有对应功能的 PRD 则同步更新，否则无需创建新文档 |
