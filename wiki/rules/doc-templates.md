# 文档结构模板

> **按需加载文件**：本文件是 [doc-rules.md](doc-rules.md) §5 的拆分内容（27.7 KB 纯模板），
> 仅在**创建或大幅修订** PRD / SDD / TC / PROTO 文档、需要章节骨架时读取；
> 查阅同步原则、命名、版本管理等规则时读 doc-rules.md 即可，不要读本文件。
> 章节编号沿用原 §5（如 §5.2 指 SDD 结构），外部引用不受影响。

## 5. 文档结构规范

除经验库外，PRD/SDD/TC/SOP 四类正式文档均遵循以下通用约定：

| 约定 | 说明 |
| --- | --- |
| 固定二级编号 | 采用**固定二级章节编号**，禁止自行调整顺序或增删章节 |
| 级别标注 | 各章标注 `[必须]` 或 `[按需]`；`[按需]` 根据模块实际情况决定是否包含 |
| 同级一致 | 同层级模块的同类型文档**必须保持二级章节编号一致** |
| mermaid 图表 | 文档中所有图表（架构图、流程图、时序图、ER 图、类图、状态图等）**必须使用 mermaid** 代码块绘制，禁止以截图或外部图片代替。mermaid 代码块使用 4 空格缩进，禁止 tab。**结构类图表（功能架构图、界面功能架构图、模块划分图等）使用左右布局 `graph LR`，禁止上下布局 `graph TD`**；流程/状态类图表（流程图、状态机图、时序图）按内容适配。mermaid 代码块属图表描述语言，**不视为 §7 所禁止的代码** |
| Markdown 表格 | **禁止**使用空格填充列宽做视觉对齐。分隔符 `|` 两侧各留一个空格，单元格内容前后不添加对齐空格 |

各类型详细结构如下：

### 5.1 PRD 需求文档

#### 第 1 章 — 文档概述 `[必须]`

| 编号 | 章节 | 内容 | 级别 |
| --- | --- | --- | :--: |
| 1.1 | 文档信息 | 文档版本、创建/更新日期、基于需求 | 必须 |
| 1.2 | 变更记录 | 版本降序，每版一行 | 必须 |
| 1.3 | 项目背景 | 业务背景、要解决的核心问题 | 必须 |
| 1.4 | 功能概述 | 功能范围、核心能力描述 | 必须 |
| 1.5 | 目标用户 | 用户角色定义、各角色使用场景 | 必须 |

#### 第 2 章 — 需求全景 `[必须]`

| 编号 | 章节 | 内容 | 级别 |
| --- | --- | --- | :--: |
| 2.1 | 功能架构 | 使用 mermaid 功能结构图展示功能的层次关系和整体组成，让读者在进入细节前建立全局认知 | 必须 |
| 2.2 | 功能模块划分 | 各功能域的职责范围与边界，说明每个功能域解决什么问题、包含哪些子功能 | 必须 |
| 2.3 | 功能依赖关系 | 功能域之间的前置依赖和关联关系（如 A 功能的数据需 B 功能先配置），使用 mermaid 绘制依赖图 | 必须 |
| 2.4 | 界面功能架构 | 定义悬浮窗的界面区块与入口（标题栏 / 列表区 / 滚动条 / 右键菜单项 / 自选管理面板）与「入口—功能点」映射，作为 PROTO 与 SDD 界面设计的依据 | 必须 |

> **2.4 界面功能架构**：本项目无网页导航菜单，入口只有三类——**窗口区块**（标题栏、列表区、滚动条）、**右键菜单项**、**自选管理面板中的控件**。PRD 必须显式列出全部入口，作为 PROTO 与 SDD §3.5 界面设计的依据。要求：
>
> - 用 mermaid 绘制入口结构，入口名称与最终产品文案一致（右键菜单项的 label 即产品文案）；该结构描述「用户从哪里触发功能」，**区别于 §2.1 功能架构图**（业务能力层次）
> - **入口层级定义**：一级 = 窗口区块；二级 = 区块内的可交互元素（如列表行、滚动条滑块）或右键菜单项；三级 = 面板内的具体控件（如「管理自选」面板中的搜索框、添加按钮）
> - 用映射表逐项列出：入口名称、所在层级、触发方式（点击 / 双击 / 拖动 / 滚轮 / 右键）、功能路径（§3.2）、对应功能点（§3.2 F-xx）、对应功能域（§2.2 M-xx）
> - **与 §3.2 功能路径的关系**：§3.2 功能路径是功能的逻辑层级，§2.4 是用户触发入口，两者须通过映射表的「功能路径」列一一对应，不得出现两套互不关联的层级
> - 映射完整性：每个入口必须对应至少一个功能点；一个功能点可有多个入口（多入口须显式标注）；不得出现无功能点的入口或无入口的功能点
> - **一致性校验方法**：PROTO 的界面元素、SDD §3.5 的元素清单必须逐项对照本表核验（名称、层级、触发方式、对应功能点四项一致），不得自行增删改
> - 如需调整入口，先改 PRD 本表并级联更新 PROTO/SDD

#### 第 3 章 — 功能需求 `[必须]`

| 编号 | 章节 | 内容 | 级别 |
| --- | --- | --- | :--: |
| 3.1 | 用户故事 | 角色-活动-价值格式的用户故事 | 必须 |
| 3.2 | 详细功能点 | 每个功能点独立成节，包含：功能路径（`一级 → 二级 → 三级`）、功能描述、触发条件、输入字段定义表（字段名/类型/必填/校验规则/默认值/说明）、业务处理逻辑（步骤/条件分支/状态变更）、输出结果（成功/失败反馈/副作用）、交互流程。禁止将多个功能压缩为一行表格记录 | 必须 |
| 3.3 | 业务规则 | 按子功能域分节，每节包含：业务约束（约束条件/适用范围/违反处理）、业务状态机（状态列表含编码含义 + mermaid stateDiagram 流转图 + 每个流转的前置条件与触发动作）、业务逻辑规则（触发条件/执行动作/优先级）。禁止仅罗列零散列表项 | 必须 |
| 3.4 | 业务流程 | 端到端业务操作链路，使用 mermaid 流程图或用户旅程图，展示功能之间的串联关系和用户操作路径（如"制定计划 → 提交审批 → 触发任务 → 执行巡检 → 审核结果"）。区别于 SDD 的技术实现级流程，PRD 流程聚焦用户视角的业务闭环 | 必须 |

> **3.2 字段定义表**：涉及数据录入/展示的功能点，输入和输出字段必须以表格形式逐字段定义，禁止仅用自然语言概述。字段表至少包含：字段名、类型（文本/数字/下拉单选/下拉多选/日期/布尔等）、必填（是/否）、校验规则（格式/长度/取值范围/唯一性）、默认值、字段说明。
>
> **3.2 功能路径**：功能路径格式为 `一级 → 二级 → 三级`（层级数按实际情况，不强制三级）。功能路径描述功能点在系统中的层级位置（纯功能层级，非 UI 菜单名、非 URL 路由）。任意层级都可能是功能页面。不确定时向用户确认。
>
> **3.3 编写要求**：
>
> - **业务约束**：须包含约束条件、适用范围、违反时的处理方式（阻止操作 / 警告但允许 / 允许并记录日志）
> - **业务状态机**：须包含状态列表（状态名/编码/含义）、mermaid stateDiagram 流转图、每个流转的前置条件和触发动作（谁可触发 / 操作入口 / 触发后系统做什么）
> - **业务逻辑规则**：须包含触发条件、执行动作、优先级（多条规则冲突时的裁决顺序）
>
> **3.2 与 3.3 的边界**：3.2 描述单个功能的字段级定义和操作步骤；3.3 描述跨功能的业务规则（如状态如何流转、删除关联数据时级联策略、配置变更如何传播）。
>
> PRD 内容边界：只描述"做什么"，不涉及"怎么做"。禁止包含第三方接口地址、`config.json` 字段结构、函数/类名、Python 版本与库名。

#### 第 4 章 — 非功能性需求 `[必须]`

| 编号 | 章节 | 内容 | 级别 |
| --- | --- | --- | :--: |
| 4.1 | 性能要求 | 每项指标须给出具体目标值和测量条件（如：行情刷新间隔 ≤ 5s、单次刷新网络耗时 < 800ms、窗口重绘无可见卡顿、常驻内存 < 80MB、非交易时段 CPU 占用接近 0），禁止仅罗列指标名称而无具体数值 | 必须 |
| 4.2 | 安全要求 | 只读公开行情数据、无用户凭据存储、配置文件不外发 | 按需 |
| 4.3 | 兼容性要求 | Windows 版本、DPI 缩放比例（100%~200%）、屏幕分辨率下限、多显示器 | 按需 |

#### 第 5 章 — 验收标准 `[必须]`

| 编号 | 章节 | 内容 | 级别 |
| --- | --- | --- | :--: |
| 5.1 | 功能验收条件 | 对照 3.2 每个功能点逐一列出验收标准，每条包含：前置条件、操作步骤、预期结果。每个输入字段的校验规则（必填/格式/范围）须有对应的验收条目，禁止笼统描述如"功能正常" | 必须 |

#### 第 6 章 — 原型交付 `[按需]`

| 编号 | 章节 | 内容 | 级别 |
| --- | --- | --- | :--: |
| 6.1 | HTML 原型 | 基于 ui-rules.md 的页面原型，单文件自包含 | 按需 |

> 原型风格强制依据 ui-rules.md，不得脱离规范自行设计视觉。

### 5.2 SDD 设计文档

#### 第 1 章 — 文档概述 `[必须]`

| 编号 | 章节 | 内容 | 级别 |
| --- | --- | --- | :--: |
| 1.1 | 文档信息 | 文档版本、创建/更新日期、基于需求、基于设计 | 必须 |
| 1.2 | 变更记录 | 版本降序，每版一行 | 必须 |
| 1.3 | 技术选型 | Python 版本、GUI 框架（tkinter）、数据来源（腾讯行情接口）、配置存储（JSON 文件） | 必须 |
| 1.4 | 文档目的 | 本模块设计目标、要解决的问题、模块职责范围 | 必须 |

#### 第 2 章 — 系统架构 `[必须]`

| 编号 | 章节 | 内容 | 级别 |
| --- | --- | --- | :--: |
| 2.1 | 整体架构 | 系统分层架构图 | 必须 |
| 2.2 | 模块划分 | 模块拆分方案、各模块职责与边界 | 必须 |
| 2.3 | 分层职责 | 窗口与绘制层（tkinter Canvas）/ 行情获取层（urllib + 腾讯接口）/ 配置与持久化层（config.json、position.json）/ 交互层（鼠标事件与右键菜单）等各层职责说明 | 必须 |
| 2.4 | 界面区块地图 | 悬浮窗的区块划分（标题栏 / 列表区 / 滚动条 / 右键菜单 / 自选管理面板）、区块与绘图层级的对应关系；各区块须回链 PRD §2.4 的界面功能架构 | 必须 |

#### 第 3 章 — 详细设计 `[必须]`

| 编号 | 章节 | 内容 | 级别 |
| --- | --- | --- | :--: |
| 3.1 | 数据模型 | 配置文件与内存结构（`config.json` 的字段名/类型/默认值/约束、`position.json` 字段），结构关系用 `classDiagram` 或 JSON 示例说明 | 必须 |
| 3.2 | 外部接口设计 | 每个外部接口独立成节，包含：接口地址、请求方式、请求参数、返回报文（含字段含义与示例）、编码与异常约定。本项目无自建服务端，本节描述所依赖的第三方行情接口 | 必须 |
| 3.3 | 业务流程 | 对照 PRD §3.4 描述的每一条业务链路，逐条给出技术实现级时序图，标注参与者、消息流向和处理步骤。禁止只挑一条"核心"链路而忽略其他链路 | 必须 |
| 3.4 | 业务规则 | 对照 PRD §3.3 的每条业务规则（业务约束/状态机/逻辑规则），逐条给出技术实现方案 | 必须 |
| 3.5 | 界面设计 | 存在 PROTO 时：引用 PROTO 路径，补充画布元素树与绘制函数映射、状态变量（折叠/滚动/缩放/拖动中）。无 PROTO 时：窗口布局、坐标与尺寸计算、交互流程、视觉状态（颜色/字体/圆角） | 按需 |
| 3.6 | 错误处理定义 | 异常场景（网络失败/接口返回异常/配置损坏/文件写入失败）、提示方式（标题栏圆点颜色/静默降级）、日志记录策略 | 必须 |
| 3.7 | 其他设计 | 类与函数设计（核心类/方法及调用关系）、数据结构设计（字段/类型/默认值）、常量定义（名称/取值/说明）、线程与定时器机制、版本管理机制等 | 按需 |
| 3.8 | 功能点追溯 | 对照 PRD §3.2 每个功能点，逐一标注对应的技术产物 | 必须 |

> **§3.5 界面设计**：PROTO 是用户确认后的正式交付物，具有约束力。存在 PROTO 时，§3.5 引用 PROTO 文件路径，不再重复描述布局和交互，只补充技术层面内容（画布元素与绘制函数的对应关系、状态变量、坐标与尺寸换算）。无 PROTO 时，完整描述窗口布局、交互流程、视觉状态。
>
> **§3.3 业务流程**：逐条用 mermaid 时序图呈现技术实现，标注参与者、消息流向和处理步骤。仅当流程本质不适配时序图时（如纯算法步骤、规则决策树），可使用流程图替代。时序图统一置于 §3.3 业务流程中。
>
> **§3.8 功能点追溯**：对照 PRD §3.2 的每个功能点，逐一标注对应的技术产物。功能点编号与名称须与 PRD §3.2 一致，无对应时写 `—`。按功能点分行，技术产物逐行列于下方。
>
> **API 响应示例格式**：响应示例使用 ` ```json ` 表示，属 SDD 内容边界的一部分，**不视为违反 §7 代码引用规则**。

#### 第 4 章 — 代码位置 `[按需]`

每个代码位置行回链 §3 的对应设计产物（标注 §3 子节编号），确保 AI 不猜测设计到代码的映射关系。

##### 4.1 程序逻辑

| 编号 | 章节 | 内容 | 级别 |
| --- | -- | --------------------------------- | :-: |
| 4.1 | 程序逻辑 | 设计产物（§3 章节）/ 文件 / 函数·方法 / 说明 | 按需 |

> **映射粒度**：行情获取、业务规则、流程节点按**函数级**映射（`模块名.函数名`，如 `ticker.Panel.build`）；数据模型按**字段级**映射（`config.json` 的键名）；常量按**文件级或常量名级**映射。

##### 4.2 界面绘制

| 编号 | 章节 | 内容 | 级别 |
| --- | -- | ------------------------------------ | :-: |
| 4.2 | 界面绘制 | 设计产物（§3 章节）/ 文件 / 绘制函数·画布元素 ID / 说明 | 按需 |

> **映射粒度**：区块按**函数级**映射（`build` / `paint` / `update_scrollbar` 等绘制函数）；画布元素按**元素 ID 级**映射（`create_text` 返回的 item id 或标签名）；交互按**事件处理函数级**映射（`on_press` / `on_drag` / `on_wheel` 等）。

##### 4.3 配置与脚本位置

| 编号 | 章节 | 内容 | 级别 |
| --- | ------- | ---------------------------------- | :-: |
| 4.3 | 配置与脚本位置 | 设计产物（§3 章节）/ 文件 / 路径 / 文件·配置项 / 说明 | 按需 |

> 覆盖 `config.json` 的配置项、`position.json` 的位置持久化、`启动盯盘.bat` 启动脚本、开机自启注册（启动文件夹 .vbs）等非代码文件的变更位置。操作类型（新增/修改/删除）标注在"说明"列。
>
> **与 §6.3 的区别**：§4.3 描述配置**写在哪里**（位置信息，给程序员），§6.3 描述**上线时要配什么值、在哪个环境执行**（部署内容，给运维）。

#### 第 5 章 — 依赖关系 `[必须]`

| 编号 | 章节 | 内容 | 级别 |
| --- | --- | --- | :--: |
| 5.1 | 内部模块依赖 | 本模块与其他模块之间的调用关系和数据依赖 | 必须 |
| 5.2 | 外部系统依赖 | 腾讯行情接口 `qt.gtimg.cn`（行情）、`smartbox.gtimg.cn`（标的搜索）、操作系统 Win32 API（窗口圆角/透明/置顶）等 | 必须 |

> 依赖关系须注明依赖方向（单向/双向）和依赖目的。
>
> **与第 7 章的区别**：第 5 章描述模块间**通用的静态依赖**（本模块正常运行依赖哪些模块的哪些能力），第 7 章描述**特定业务场景下的动态交互**（本业务中模块间如何协作调用）。通用依赖写第 5 章，场景级交互写第 7 章。

| 编号 | 章节 | 内容 | 级别 |

| 6.2 | 关键配置项 | `config.json` 中的核心参数名称、默认值、说明 | 必须 |
| 6.3 | 发布配置清单 | 配置类型（config.json/启动脚本/开机自启）/ 配置名称 / 变更内容 / 执行环境 / 顺序依赖 | 按需 |

> 代码引用须遵守 [§7 SDD 代码引用规则](#7-sdd-代码引用规则)——禁止直接粘贴 Python 源码/JSON 配置文件。
>

### 5.4 经验库文档

经验库用于记录开发过程中积累的经验教训，遵循**简洁优先**原则，不纳入版本管理体系。目录结构见第 3 节。

| 章节 | 内容 |
| --- | --- |
| 1. 问题 | 一句话描述遇到的问题 |
| 2. 做法 | 解决该问题的具体步骤或方法（列表形式） |
| 3. 效果 | 量化或定性描述解决后的效果 |
| 4. 适用场景 | 该经验适用的上下文条件 |

**编写原则**：

| 原则 | 要求 |
| --- | --- |
| 字数限制 | 每条经验不超过 200 字 |
| 结构要求 | 问题 → 做法 → 效果，三部分即可 |
| 粒度控制 | 一条经验解决一个具体问题 |
| 灵活策略 | 允许只包含问题和做法（半条经验） |

**与正式文档的区别**：

| 对比项 | PRD/SDD/TC | 经验库 |
| --- | --- | --- |
| 版本管理 | 三段式版本号，变更留痕 | 无需版本号 |
| 头部信息 | 必须包含文档信息表、变更记录 | 无需头部信息 |
| 更新方式 | 版本迭代，保留旧版 | 直接修改，持续演进 |
| 内容边界 | 严格按类型划分 | 自由记录，无边界限制 |
