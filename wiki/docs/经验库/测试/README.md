# 测试经验

此处存放测试过程中积累的经验。

## 测试脚本必须隔离数据目录（2026-10-30 事故）

**事故**：K 线布局回归脚本用临时 `panel.cfg = {"kline": {...}}` 构造测试桩，
`KlineWin.close()` → `save_state()` → `save_kline_state(cfg)` → `save_json(CONFIG_FILE, cfg)`
把**真实 config.json 整份覆盖**成只剩 `kline` 一项，用户的两个分组（7 个指数 + 19 个自选）
全部丢失，界面表现为「自选都没了」。

**根因**：`ticker.pyw` 的数据文件路径在模块导入时按 `BASE` 固定；测试桩 import 真模块后，
任何「保存」动作都会落到真实文件上。测试没有意识到自己也接上了生产数据。

**修复（三层）**：

1. **环境变量隔离**：`BASE = os.environ.get("MARKETWIDGET_BASE") or <脚本目录>`，
   测试脚本 import 前设 `os.environ["MARKETWIDGET_BASE"] = tempfile.mkdtemp(...)`；
   现在 `tc_kline2.py` / `tc_kline_live.py` / `tc_kline_openfit.py` 全部走临时目录，
   md5 校验真实 config.json 在测试前后不变。
2. **写盘留底**：`save_json()` 覆盖前先把旧文件复制成 `.bak`，任何整份覆盖事故都能人工回滚。
3. **窄函数防丢**：`save_kline_state()` 只负责 `kline` 键，若传入 cfg 缺 `groups`，
   先把磁盘上的其它键并回来再写——单点修掉「K 线记忆写掉整份配置」这类路径。

**通用原则**：任何「import 真程序 + 触发真实副作用」的测试，先隔离所有落盘路径
（配置、缓存、日志、数据库），并用校验和断言「真实文件未被触碰」。数据能恢复是运气
（本次靠历史会话里的一条 11:02 快照 + 17:10 selftest 的代码顺序比对），不能当流程。

## Tk 合成鼠标事件：双击不可合成，事件时间必须与 Tk 同源（2026-10-30）

**问题**：自动化驱动 K 线窗口时，`event_generate("<Double-Button-1>")` 直接抛
`TclError: Double, Triple, or Quadruple modifier not allowed`；改用单次
`<Button-1>` 连发模拟双击，又出现「拖动后视图被莫名复位」，`view_off` 在两次拖动
之间被清零。

**根因**：
1. Tk 不允许合成多击事件，双击只能由两次 PRESS 的时间差在 Tk 内部判定；
2. `event_generate` 不传 `time` 时所有事件时间戳相同 → **任意相邻两次 PRESS 都被
   判成双击** → 触发 `on_double` → `reset_view()`；
3. 传 `time` 又踩两个坑：`time.time()*1000`（1.7e12）超出 Tk 的 32 位 → 抛
   「integer value too large to represent」；随意换成小数值后，合成事件与真实
   事件时间不可比，负差被当作 0，仍然误判双击。

**做法**：
1. 双击一律**直调真实处理函数**（`app.on_double(_E(x, y))` / `kw.reset_view()`），
   不走事件合成；
2. 必须合成时，事件时间基值取 `GetTickCount()`（Tk 在 Windows 上就用它），
   每次 +600ms 单调递增并掩到 32 位内。

**效果**：回溯 / 拖动 / 双击复位三条用例从「不稳定」变为稳定通过；定位过程靠
`__setattr__` 钩子抓 `view_off` 写入来源，比读代码猜快得多。

**适用场景**：任何用 `event_generate` 驱动 Tk 界面的自动化测试。

## 截图要抓窗口自身的位图，不要抓屏幕（2026-10-30）

**问题**：`ImageGrab.grab(bbox=...)` 截出来的全是桌面壁纸，K 线窗口、主面板一律
不可见，147 张「证据截图」全部无效。

**根因**：本机会话的桌面不做窗口合成（远程/无头式会话），屏幕帧里没有窗口内容，
而 `winfo_width/height` 与窗口实际渲染都正常——只有「读屏幕」这一条路失效。

**做法**：用 `PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT=2)` + `GetDIBits` 直接取
窗口位图；句柄取 `winfo_id()`，尺寸取 `winfo_width/height`，得到的就是客户区像素，
与画布坐标一一对应。ctypes 调用必须声明 `argtypes/restype`（句柄 > 2^31 会 overflow）。

**效果**：截图恢复为真实界面（标题栏、K 线、MACD 副图齐全），像素级取色断言也可用。

**适用场景**：Windows 上任何需要截图留证的 Tk/Win32 自动化。

## 桩数据缓存要按「最大可能需求」建，否则回溯类用例必然假失败（2026-10-30）

**问题**：K 线桩 `fetch_kline` 按首次请求的 `lmt` 建缓存（300/490 根），后续回溯
请求 `lmt` 更大时只能切出同样的老数据，`_merge_backtrack` 算出 `added <= 0`，
AC-12「左拖追加 250 根」稳定失败。

**做法**：桩恒定生成满量数据（如 600 根），按 `lmt` 切片返回；这样「请求更大窗口 →
拿到更多更早的根」与真实数据源行为一致。

**教训**：写桩时要按**被测代码的最坏调用**设计容量，不能按第一次调用的参数偷懒，
否则测的是桩的边界而不是产品的行为。

**适用场景**：分页 / 回溯 / 增量加载类接口的桩。

## 执行记录的「结论」列必须从日志抄，不能从需求抄（2026-10-31）

**问题**：TC §6.1 的通过项明细表写好「结论」列后，独立审核一眼判定「不通过」——
理由是全表 44 行里有 12 条以上张冠李戴：TC-F-02 写「首帧即完整布局」而日志实际断言
是「复用窗口不新开」，TC-F-21 写「重试成功恢复 K2」而日志是「K4 空态」，
TC-F-36 写「100 次重绘最差 3.31ms」而日志是 4.21ms 且属另一条用例。

**根因**：写结论时对着 PRD 的 AC 描述逐条「翻译」，而不是回读 `_run_all.log`
的 `[PASS]` 行。用例编号与 AC 编号一一对应，很容易让「预期」冒充「实测」——
数字看起来齐全，其实全是猜的。

**做法**：
1. 写 §6.1 前先用脚本把日志里每个用例的 `[PASS]` 文本抽出来（按 `^TC-xxx-\d+` 切块），
   逐块复制关键数值，禁止手打数字；
2. 结论列的每条数值必须能在日志里 grep 到，否则不写；
3. 自己抽查 3~5 个「结论与预期最像」的行——最像的地方最容易抄错。

**教训**：测试报告的可信度只取决于「结论能否追溯到原始输出」，不取决于文档多完整。
一旦被抓到一处编造，整份报告都要重审。

**适用场景**：所有带「执行结果」章节的测试文档、验收记录、上线检查单。
