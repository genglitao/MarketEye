# PRD 需求技能

本技能负责**需求整理与PRD文档生产**，是被sdlc-skill调用的环节技能之一。

## 触发条件

- sdlc-skill 评估后认为需要新增/变更功能
- 变更已有功能时需要先读取现有PRD

## 前置条件

| 条件 | 说明 |
|------|------|
| 已有PRD | 变更已有功能时必须先读取现有PRD |

## 工作流程

### 步骤1：理解用户需求

向用户收集以下信息：

**必填信息**：
- 功能名称是什么？
- 所属模块是哪个？
- 一句话描述这个功能要解决什么问题？
- 目标用户是谁？
- 功能路径（一级 → 二级 → 三级，层级数按实际情况，不确定时向用户确认）

**功能拆解**：
- 包含哪些子功能？
- 每个子功能的输入、处理、输出？
- 用户与系统的主要交互流程？

**验收标准**：
- 怎么算功能做好了？
- 成功/失败/边界的判断标准？

### 步骤2：判断需求类型

| 类型 | 后续动作 |
|------|----------|
| 新功能 | 直接生成PRD |
| 变更已有功能（未发布） | 在当前版本内修改 PRD，更新并合并当前版本已有的变更记录，禁止追加重复版本行；级联更新下游文档及 PROTO（如存在） |
| 变更已有功能（已发布） | 基于现有 PRD 生成新版本，为新版本新增唯一一行变更记录；PROTO 同步升版（如存在） |

判断方法：读取现有PRD头部的"版本状态"字段，取值为"未发布"或"已发布"。

### 步骤3：生成PRD文档

按 [doc-rules](../../rules/doc-rules.md) 生成 `PRD-{模块名}-{功能名}-v{版本号}.md`，详见该规范 §5.1。产出按该规范 §3 输出。

### 步骤4：询问并生成原型

PRD 生成完成后，主动询问用户："是否需要为这个功能生成高保真 HTML 原型？"

- **需要**：读取 [ui-rules.md](../../rules/ui-rules.md) 和当前 PRD，调用 ui-designer 产出 `PROTO-{模块名}-{功能名}-v{版本号}.html`，与 PRD 放在同一版本目录下
- **不需要**：跳过本步骤，继续执行步骤 5

### 步骤5：更新 wiki.md 索引

PRD（及 PROTO 如已生成）产出后，**必须**按 [doc-rules](../../rules/doc-rules.md) §9 同步更新 [wiki.md](../../wiki.md)：

1. **系统级/模块级 PRD** → 更新"全局"区域，追加 `- [PRD-xxx](相对路径) — 一句话摘要`
2. **功能级 PRD** → 在"业务文档"下按模块+功能定位到对应 H3/H4 标题，追加 `- [PRD-xxx](相对路径) — 一句话摘要`；无对应标题则新增

### 步骤6：独立审核

启动**独立的 Agent 实例**，依据 [doc-rules](../../rules/doc-rules.md) §4、§5.1 和 §6.1 对产出的 PRD 文档进行合规性审核。产生 PRD 的 AI 不得自行审核。

独立审核必须包含变更记录唯一性检查：

- 同一文档的每个版本号必须有且仅有一行变更记录。
- 未发布版本多次调整后，变更内容必须合并在当前版本原记录中。
- 发现重复版本号时必须判定不通过，不得以“记录调整过程”为理由保留重复行。

审核通过后流程结束，等待用户指示下一步。
