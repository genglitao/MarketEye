# SDLC 流程辅助

本技能是 **SDLC流程的辅助工具**，根据用户诉求判断应使用的环节技能，并检查前置条件是否满足。

## 核心职责

1. **判断技能** - 根据用户诉求推断应使用哪个环节技能
2. **检查前置条件** - 确保依赖文档齐全
3. **引导补充** - 遇到文档缺失时，先引导补充文档再继续

## 环节技能

| 技能 | 职责 | 触发条件 |
| ---- | ---- | -------- |
| prd-skill | 需求整理 + PRD文档 | 需要新增功能或变更已有功能 |
| sdd-skill | 详细设计 + SDD文档 | 需要技术设计 |
| coding-skill | 按设计文档编码 | 需要实现功能 |
| test-skill | 按文档进行验收测试 | 需要验证功能 |

## 环节前置条件

> ⚠️ **重要说明**：「例外情况」描述的是**额外的准备工作**，并不意味着跳过该环节。所有环节在有对应诉求时都必须执行。

| 环节 | 前置依赖 | 执行条件 |
| ---- | -------- | -------- |
| prd-skill | 无 | 新功能开发：直接执行<br>变更已有功能：**先读取现有PRD**，再执行 |
| sdd-skill | 需求文档(PRD) | 有PRD：读取后执行；如有 PROTO 一并读取<br>纯技术框架设计：不需要PRD，直接执行 |
| coding-skill | 需求+设计文档(PRD+SDD) | 业务需求：PRD+SDD 版本对齐；如有 PROTO 则须 PRD/PROTO/SDD 三方内容一致性检查通过<br>纯技术变更：只需 SDD，执行 |
| test-skill | 需求+设计文档(PRD+SDD) | 功能验收：PRD+SDD 齐全后执行；如有 PROTO 一并读取<br>纯技术变更验收：只需 SDD，执行 |

### 判断示例

| 诉求 | 判断结果 | 理由 |
|------|----------|------|
| 新增一个功能 | prd-skill ✅ | 无前置依赖，直接执行 |
| 变更已有功能 | prd-skill ✅ + 先读现有PRD | 需先读取现有PRD作为输入 |
| 技术框架设计 | sdd-skill ✅ | 例外情况：不需要PRD |
| 业务功能实现 | prd-skill + sdd-skill + coding-skill | 需 PRD+SDD 版本对齐 |
| 纯技术变更实现 | sdd-skill + coding-skill | 例外情况：只需 SDD |

## 触发方式

### 方式一：用户描述诉求，AI判断

```
用户: "我想新增一个XXX功能"
→ 判断：需要prd-skill

用户: "我需要对XXX功能进行技术设计"
→ 判断：需要sdd-skill

用户: "我要对XXX功能进行测试"
→ 判断：需要test-skill

用户: "XXX功能有问题"
→ 判断：Bug修复，需要检查是否有PRD
```

### 方式二：用户指定技能

```
用户: "用prd-skill帮我整理需求"
→ 接受，但检查前置条件是否满足
→ 如前置条件不满足，提示补充后再继续
```

### 方式三：用户使用标准命令格式

当用户使用标准格式描述诉求时，直接路由到对应技能：

| 用户诉求格式 | 应启动技能 |
|------------|----------|
| 新增/调整xx功能 | prd-skill |
| 设计xx版本需求 | sdd-skill |
| 编码xx版本需求 | coding-skill |
| 测试xx版本需求 | test-skill |

**示例：**
- "我要新增设备类型功能" → prd-skill
- "我要设计设备类型v1.0.1版本" → sdd-skill
- "我要编码设备类型v1.0.1版本" → coding-skill
- "我要测试设备类型v1.0.1版本" → test-skill

### Bug修复处理

修复Bug时，必须先经过 sdlc-skill 判断路由，并确认是否有对应的需求文档(PRD)：

- **有PRD** → 经过 sdlc-skill 判断后进入 coding-skill 修复流程，需同步更新相关文档
- **无PRD** → 建议先使用 prd-skill 补充需求文档

判断方法：
1. 根据Bug描述确定涉及的功能模块
2. 按 [文档规范](../rules/doc-rules.md) §3 定义的路径，查找该模块是否有对应PRD文档
3. 有PRD → 经过 sdlc-skill 判断后进入 coding-skill 修复流程
4. 无PRD → 建议先使用 prd-skill 补充需求文档

## 流程约束

| 约束条件       | 说明             |
| ---------- | -------------- |
| 无需求，不设计    | 除非是纯技术框架设计     |
| 无需求和设计，不编码 | -              |
| 无需求和设计，不测试 | -              |
| 功能与需求不一致   | 必须走变更流程，重新评估需求 |
| 文档间不一致，不编码 | 编码前必须检查 PRD/PROTO/SDD 内容一致性（有 PROTO 则三方一致，无 PROTO 则两方一致），不一致时禁止进入编码环节，须先修正文档 |

## 单次执行原则

**每个环节技能完成后必须停下来，等待用户明确指示后再执行下一个环节。**

| 用户诉求       | 行为                            |
| ---------- | --------------------------------- |
| 需求变更       | 调用 prd-skill，完成后停下来等待用户指示  |
| 用户说"开始设计"  | 调用 sdd-skill，完成后停下来等待用户指示 |
| 用户说"按设计实现" | 调用 coding-skill                |
| 用户说"开始测试"  | 调用 test-skill                  |
| 功能与需求不一致   | 调用 prd-skill 重新评估需求             |

> sdlc-skill 只负责判断用哪个技能，不会链式触发后续所有技能。

## 前置审视

每个环节技能在**输出交付物之前**，必须执行前置审视。

### 审视流程

**1. 构建决策树（静默）**

输出前，内心梳理：哪些决策已锁定？哪些还存在歧义？依赖了什么未敲定的东西？隐含了什么假设？

**2. 对话审视**

切换到对抗模式，向用户提问。每次只问一个问题，附带推荐答案及理由，等待用户回应后再推进。

规则：
- **追到底**：当前分支穷尽后再开新分支
- **不接受弱推理**："应该没问题""一般不会出问题"视为未通过，追问到具体理由
- **代码能回答的不提问**：先查代码再开口

**3. 收尾**

审视结束后，简述：确认了什么、修改了什么、还有什么待定。

### 约束

审视通过后方可输出交付物。审视过程保持对话，用户在场自然终止，不追求穷尽所有维度。

## 按需加载 — 文档加载场景

> 文档命名和结构遵循 [文档规范](../rules/doc-rules.md)。

| 环节 | 场景           | 行为                                 |
| -- | ------------ | ---------------------------------- |
| 需求 | 了解项目背景和目标    | 读取系统级 PRD                      |
| 需求 | 了解业务流程       | 读取对应 PRD 的功能需求部分，或 SDD 的详细设计部分 |
| 需求 | 功能变更时        | 先读取对应模块的 PRD                     |
| 设计 | 了解系统架构和技术选型  | 读取系统级 SDD 的文档概述和系统架构部分      |
| 设计 | 查看数据模型定义     | 读取对应 SDD 的详细设计部分              |
| 设计 | 了解外部接口规范     | 读取对应 SDD 的详细设计部分              |
| 设计 | 了解界面布局和交互预期  | 如有 PROTO，读取原型                    |
| 编码 | 了解需求背景和业务目标  | 读取对应模块的 PRD                      |
| 编码 | 了解现有代码结构     | 读取对应模块代码                           |
| 编码 | 确认代码是否符合设计要求 | 读取对应模块的 SDD                      |
| 编码 | Bug定位与修复     | 读取对应模块的 PRD 和 SDD，了解预期行为和正确实现 |
| 编码 | 还原视觉和交互效果    | 如有 PROTO，读取原型                    |
| 测试 | 功能验收         | 读取对应模块的 TC                |
| 测试 | 回归测试         | 读取对应模块的 TC，确认修改未破坏现有功能    |
| 测试 | 缺陷复现和定位      | 读取对应模块的 PRD 和 SDD，了解预期行为      |
| 测试 | 集成测试         | 读取系统级 SDD 的依赖关系部分，确认跨模块交互   |
| 测试 | 视觉对照验证       | 如有 PROTO，读取原型                    |

## 注意事项

- 本技能是辅助判断工具；用户明确指定技能时可直接使用，但仍需检查前置条件
- 无论哪种触发方式，前置条件约束始终生效
- 遇到文档缺失时，先引导补充文档再继续流程
- 判断标准是**是否有文档**，不是主观评估影响范围
